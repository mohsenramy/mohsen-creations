Here's a detailed guide on **Advanced Design Patterns** in JavaScript/TypeScript:

### 1. Core Concept and Significance

**Advanced Design Patterns** extend beyond the fundamental categories of design patterns—creational, behavioral, and structural—by providing solutions to more complex problems encountered in software design. These patterns help improve code organization, maintainability, and scalability while promoting code reuse and reducing redundancy. Understanding these patterns can significantly enhance a developer's ability to architect robust software systems.

### 2. Code Examples with Comments

Here are several advanced design patterns along with their implementations in TypeScript:

#### a. **Decorator Pattern**

The Decorator Pattern allows behavior to be added to individual objects, either statically or dynamically, without affecting the behavior of other objects from the same class.

```typescript
// Base interface for the component
interface Coffee {
  cost(): number;
}

// Concrete implementation of the Coffee component
class SimpleCoffee implements Coffee {
  cost(): number {
    return 5; // Base cost of a simple coffee
  }
}

// Decorator class for adding additional features
class MilkDecorator implements Coffee {
  private coffee: Coffee;

  constructor(coffee: Coffee) {
    this.coffee = coffee; // Injecting the coffee component
  }

  cost(): number {
    return this.coffee.cost() + 2; // Adding the cost of milk
  }
}

// Decorator for adding sugar
class SugarDecorator implements Coffee {
  private coffee: Coffee;

  constructor(coffee: Coffee) {
    this.coffee = coffee; // Injecting the coffee component
  }

  cost(): number {
    return this.coffee.cost() + 1; // Adding the cost of sugar
  }
}

// Example usage
const myCoffee = new SimpleCoffee();
const myMilkCoffee = new MilkDecorator(myCoffee);
const myFancyCoffee = new SugarDecorator(myMilkCoffee);

console.log(myFancyCoffee.cost()); // Output: 8 (5 + 2 + 1)
```

#### b. **Observer Pattern**

The Observer Pattern defines a one-to-many dependency between objects so that when one object changes state, all its dependents are notified and updated automatically.

```typescript
// Subject interface
interface Subject {
  subscribe(observer: Observer): void;
  unsubscribe(observer: Observer): void;
  notify(): void;
}

// Observer interface
interface Observer {
  update(data: string): void; // Update method to be implemented by observers
}

// Concrete subject implementation
class WeatherStation implements Subject {
  private observers: Observer[] = [];
  private temperature: string;

  subscribe(observer: Observer): void {
    this.observers.push(observer); // Adding an observer
  }

  unsubscribe(observer: Observer): void {
    this.observers = this.observers.filter((obs) => obs !== observer); // Removing an observer
  }

  notify(): void {
    for (const observer of this.observers) {
      observer.update(this.temperature); // Notifying all observers
    }
  }

  setTemperature(temperature: string): void {
    this.temperature = temperature; // Updating the state
    this.notify(); // Notifying observers of the change
  }
}

// Concrete observer implementation
class WeatherDisplay implements Observer {
  update(data: string): void {
    console.log(`The new temperature is: ${data}`); // Handling the updated data
  }
}

// Example usage
const weatherStation = new WeatherStation();
const display = new WeatherDisplay();

weatherStation.subscribe(display);
weatherStation.setTemperature('22°C'); // Output: The new temperature is: 22°C
```

TypeScript has built-in support for interfaces and abstract classes, which can be leveraged in many design patterns to create robust type-safe designs. The use of interfaces ensures that different components adhere to a specific contract, promoting loose coupling and easier testing.

### 4. Practical Use Case

#### Use Case: Logging System

Consider a logging system where you might want to dynamically add different logging capabilities (like logging to a file, database, or console) without modifying the core logging functionality. The **Decorator Pattern** allows you to wrap the base logging functionality with additional features like formatting, filtering, or persisting logs.

### 5. Common Mistakes and Best Practices

- **Overusing Patterns:** Avoid using design patterns unnecessarily; sometimes, simpler solutions may be more effective. Understand the problem before applying a pattern.
- **Mixing Concerns:** Keep your patterns focused on specific concerns. For instance, don't mix the Observer pattern with the Decorator pattern in the same class without a clear separation of responsibilities.
- **Documentation:** Always document your patterns and their usages clearly to ensure maintainability and ease of understanding for future developers.

### Additional Design Patterns Beyond the Common Types

- **Chain of Responsibility:** Allows multiple handlers to process a request without the sender needing to know which handler will handle it.

  ```typescript
  // Handler interface
  interface Handler {
    setNext(handler: Handler): Handler;
    handle(request: string): string | null;
  }

  // Abstract handler implementation
  abstract class AbstractHandler implements Handler {
    private nextHandler: Handler;

    setNext(handler: Handler): Handler {
      this.nextHandler = handler;
      return handler;
    }

    handle(request: string): string | null {
      if (this.nextHandler) {
        return this.nextHandler.handle(request); // Passing the request to the next handler
      }
      return null;
    }
  }

  // Concrete handler
  class ConcreteHandlerA extends AbstractHandler {
    handle(request: string): string | null {
      if (request === 'A') {
        return `Handler A processed request: ${request}`;
      }
      return super.handle(request); // Pass the request to the next handler
    }
  }

  // Example usage
  const handlerA = new ConcreteHandlerA();
  const result = handlerA.handle('A');
  console.log(result); // Output: Handler A processed request: A
  ```

- **Command Pattern:** Encapsulates a request as an object, thereby allowing parameterization of clients with queues, requests, and operations.

  ```typescript
  // Command interface
  interface Command {
    execute(): void;
  }

  // Concrete command implementation
  class LightOnCommand implements Command {
    private light: Light;

    constructor(light: Light) {
      this.light = light; // Injecting the light object
    }

    execute(): void {
      this.light.turnOn(); // Executing the command
    }
  }

  class Light {
    turnOn(): void {
      console.log('The light is on!');
    }
  }

  // Example usage
  const light = new Light();
  const lightOn = new LightOnCommand(light);
  lightOn.execute(); // Output: The light is on!
  ```

**Dependency Injection (DI)** is an advanced design pattern used in software development to achieve Inversion of Control (IoC) between classes and their dependencies. Instead of a class creating its dependencies internally, those dependencies are provided (or injected) externally, which enhances the flexibility and testability of the code.

### 1. Core Concept and Significance

**Core Concept:**
Dependency Injection allows you to decouple the instantiation of a class from its usage. This means that a class does not need to know how to create its dependencies; instead, they are provided by an external entity (often a DI container). This leads to better separation of concerns, improved code maintainability, and easier testing.

**Significance:**

- **Testability:** Makes unit testing easier by allowing you to inject mock dependencies.
- **Flexibility:** Enables swapping out implementations without modifying the dependent class.
- **Maintainability:** Reduces tight coupling, making it easier to modify or replace components.

### 2. Code Examples with Comments

Here's how you can implement Dependency Injection in TypeScript:

#### a. **Constructor Injection**

```typescript
// Service interface
interface Logger {
  log(message: string): void;
}

// Concrete implementation of Logger
class ConsoleLogger implements Logger {
  log(message: string): void {
    console.log(message); // Log to the console
  }
}

// Another concrete implementation of Logger
class FileLogger implements Logger {
  log(message: string): void {
    // Here you would write code to log to a file
    console.log(`Logging to file: ${message}`); // Simulating file logging
  }
}

// A class that depends on Logger
class UserService {
  constructor(private logger: Logger) {} // Dependency is injected via constructor

  createUser(name: string): void {
    // Logic for creating a user
    this.logger.log(`User created: ${name}`); // Logging the creation
  }
}

// Example usage
const logger = new ConsoleLogger(); // Create a logger instance
const userService = new UserService(logger); // Injecting dependency
userService.createUser('Alice'); // Output: User created: Alice
```

#### b. **Setter Injection**

```typescript
class UserServiceWithSetter {
  private logger: Logger;

  setLogger(logger: Logger): void {
    this.logger = logger; // Dependency injected via setter
  }

  createUser(name: string): void {
    if (this.logger) {
      this.logger.log(`User created: ${name}`); // Using the injected logger
    }
  }
}

// Example usage
const logger2 = new FileLogger();
const userService2 = new UserServiceWithSetter();
userService2.setLogger(logger2); // Injecting dependency via setter
userService2.createUser('Bob'); // Output: Logging to file: User created: Bob
```

### 3. TypeScript Built-in Support

TypeScript does not have built-in support for Dependency Injection; however, its strong typing features (interfaces, generics) facilitate the implementation of DI patterns. You can create DI containers using classes and interfaces to manage the lifecycle and resolution of dependencies.

### 4. Practical Use Case

**Use Case: Web Application Services**

In a web application, different services (like authentication, logging, or data fetching) may have dependencies on other services or libraries. By using Dependency Injection, you can easily swap out service implementations (e.g., switching from a mock logger to a production logger) without changing the dependent classes. This allows for flexible configurations and easier testing during development.

### 5. Common Mistakes and Best Practices

- **Overusing DI:** While DI is powerful, overusing it can lead to unnecessary complexity. Use it when it genuinely improves code organization.
- **Circular Dependencies:** Be cautious of creating circular dependencies, where two classes depend on each other. This can lead to difficult-to-debug scenarios.
- **Single Responsibility Principle:** Ensure that your classes adhere to the single responsibility principle. If a class is responsible for managing its dependencies, it may become bloated.
- **Using a DI Container:** Consider using a DI container/library for larger applications to manage the lifecycle of dependencies automatically. Libraries like InversifyJS or Tsyringe can help.

### 1. **Strategy Pattern**

The Strategy Pattern defines a family of algorithms, encapsulates each one, and makes them interchangeable. This allows clients to choose the algorithm at runtime.

**Example:**

```typescript
// Strategy interface
interface SortingStrategy {
  sort(data: number[]): number[];
}

// Concrete strategy for Bubble Sort
class BubbleSort implements SortingStrategy {
  sort(data: number[]): number[] {
    // Implementing Bubble Sort algorithm
    for (let i = 0; i < data.length; i++) {
      for (let j = 0; j < data.length - 1; j++) {
        if (data[j] > data[j + 1]) {
          [data[j], data[j + 1]] = [data[j + 1], data[j]]; // Swap
        }
      }
    }
    return data;
  }
}

// Concrete strategy for Quick Sort
class QuickSort implements SortingStrategy {
  sort(data: number[]): number[] {
    // Implementing Quick Sort algorithm
    if (data.length <= 1) return data;
    const pivot = data[data.length - 1];
    const left = data.filter((x) => x < pivot);
    const right = data.filter((x) => x > pivot);
    return [...this.sort(left), pivot, ...this.sort(right)];
  }
}

// Context to use the strategy
class Sorter {
  constructor(private strategy: SortingStrategy) {}

  setStrategy(strategy: SortingStrategy): void {
    this.strategy = strategy; // Set a new strategy
  }

  sort(data: number[]): number[] {
    return this.strategy.sort(data); // Execute the strategy
  }
}

// Example usage
const sorter = new Sorter(new BubbleSort());
console.log(sorter.sort([5, 3, 8, 1])); // Output: [1, 3, 5, 8]

sorter.setStrategy(new QuickSort());
console.log(sorter.sort([5, 3, 8, 1])); // Output: [1, 3, 5, 8]
```

### 2. **Singleton Pattern**

The Singleton Pattern ensures that a class has only one instance and provides a global point of access to it.

**Example:**

```typescript
class Singleton {
  private static instance: Singleton;

  private constructor() {} // Private constructor to prevent instantiation

  static getInstance(): Singleton {
    if (!this.instance) {
      this.instance = new Singleton(); // Create instance if it doesn't exist
    }
    return this.instance; // Return the single instance
  }

  public someBusinessLogic(): void {
    // Business logic goes here
    console.log('Executing some business logic.');
  }
}

// Example usage
const singleton1 = Singleton.getInstance();
const singleton2 = Singleton.getInstance();

console.log(singleton1 === singleton2); // Output: true (both are the same instance)
singleton1.someBusinessLogic(); // Output: Executing some business logic.
```

### 3. **Facade Pattern**

The Facade Pattern provides a simplified interface to a complex subsystem. It acts as a high-level interface that makes the subsystem easier to use.

**Example:**

```typescript
// Complex subsystem classes
class Engine {
  start(): void {
    console.log('Engine started.');
  }
}

class Lights {
  turnOn(): void {
    console.log('Lights turned on.');
  }
}

class Radio {
  play(): void {
    console.log('Radio playing.');
  }
}

// Facade class
class CarFacade {
  private engine: Engine;
  private lights: Lights;
  private radio: Radio;

  constructor() {
    this.engine = new Engine();
    this.lights = new Lights();
    this.radio = new Radio();
  }

  startCar(): void {
    this.engine.start(); // Start the engine
    this.lights.turnOn(); // Turn on the lights
    this.radio.play(); // Play the radio
  }
}

// Example usage
const myCar = new CarFacade();
myCar.startCar();
// Output:
// Engine started.
// Lights turned on.
// Radio playing.
```

### 4. **Adapter Pattern**

The Adapter Pattern allows incompatible interfaces to work together. It acts as a bridge between two incompatible interfaces.

**Example:**

```typescript
// Target interface
interface Duck {
  quack(): void;
}

// Adaptee class
class Turkey {
  gobble(): void {
    console.log('Gobble gobble!');
  }
}

// Adapter class
class TurkeyAdapter implements Duck {
  private turkey: Turkey;

  constructor(turkey: Turkey) {
    this.turkey = turkey; // Injecting the Turkey instance
  }

  quack(): void {
    this.turkey.gobble(); // Adapting the Turkey's behavior
  }
}

// Example usage
const turkey = new Turkey();
const turkeyAdapter = new TurkeyAdapter(turkey);
turkeyAdapter.quack(); // Output: Gobble gobble!
```

### 5. **Memento Pattern**

The Memento Pattern allows the capture and externalization of an object's internal state without violating encapsulation, enabling the object to be restored to this state later.

**Example:**

```typescript
class Editor {
  private content: string = '';

  setContent(content: string): void {
    this.content = content; // Set content
  }

  getContent(): string {
    return this.content; // Get content
  }

  save(): Memento {
    return new Memento(this.content); // Save current state
  }

  restore(memento: Memento): void {
    this.content = memento.getContent(); // Restore state from memento
  }
}

// Memento class to store the state
class Memento {
  constructor(private content: string) {}

  getContent(): string {
    return this.content; // Get stored content
  }
}

// Example usage
const editor = new Editor();
editor.setContent('Hello, world!');
const savedState = editor.save(); // Saving state

editor.setContent('Hello, again!'); // Changing content
console.log(editor.getContent()); // Output: Hello, again!

editor.restore(savedState); // Restoring to previous state
console.log(editor.getContent()); // Output: Hello, world!
```

### 6. **State Pattern**

The State Pattern allows an object to alter its behavior when its internal state changes. It appears as if the object changed its class.

**Example:**

```typescript
// State interface
interface State {
  doAction(context: Context): void; // Method to perform an action
}

// Context class to maintain the state
class Context {
  private state: State;

  setState(state: State): void {
    this.state = state; // Set the current state
  }

  getState(): State {
    return this.state; // Get the current state
  }
}

// Concrete states
class StartState implements State {
  doAction(context: Context): void {
    console.log('Player is in start state.');
    context.setState(this); // Transitioning to new state
  }
}

class StopState implements State {
  doAction(context: Context): void {
    console.log('Player is in stop state.');
    context.setState(this); // Transitioning to new state
  }
}

// Example usage
const context = new Context();

const startState = new StartState();
startState.doAction(context); // Output: Player is in start state.

const stopState = new StopState();
stopState.doAction(context); // Output: Player is in stop state.
```
