### SOLID Principles in JavaScript/TypeScript

The SOLID principles are a set of design guidelines that help developers create more understandable, flexible, and maintainable software systems. These principles are essential in object-oriented programming and are applicable in TypeScript, which supports strong typing and class-based design patterns.

---

### 1. Core Concept and Significance

#### SOLID is an acronym that stands for:

- **S**: Single Responsibility Principle (SRP)
- **O**: Open/Closed Principle (OCP)
- **L**: Liskov Substitution Principle (LSP)
- **I**: Interface Segregation Principle (ISP)
- **D**: Dependency Inversion Principle (DIP)

These principles help developers to:

1. Reduce code complexity by dividing it into smaller, reusable parts.
2. Make the system more flexible to change.
3. Improve code readability and maintainability.
4. Reduce the risk of bugs when modifying existing code.

### 2. Principles with Code Examples

#### **1. Single Responsibility Principle (SRP)**

**Summary**: A class should have one and only one reason to change, meaning it should have only one job or responsibility.

**Code Example**:

```typescript
// Incorrect: Violates SRP - handles both user data and file operations
class User {
  saveToFile(): void {
    // File saving logic (unrelated to user)
  }
}

// Correct: Following SRP
class User {
  constructor(public name: string, public age: number) {}
}

class UserFileSaver {
  save(user: User): void {
    // Save user data to a file
  }
}

/**
 * Saves user data to a file.
 * @param user - The user object to save.
 * @returns void
 */
const saveUserToFile = (user: User): void => {
  const saver = new UserFileSaver();
  saver.save(user);
};
```

**Explanation**: The `UserFileSaver` class has a single responsibility — saving user data to a file. The `User` class is only responsible for holding user data, ensuring that each class handles only one job.

#### **2. Open/Closed Principle (OCP)**

**Summary**: Objects or entities should be open for extension but closed for modification. This means you should be able to extend a class's behavior without modifying its source code.

**Code Example**:

```typescript
// Incorrect: Modifying existing class to add new behavior
class Rectangle {
  constructor(public width: number, public height: number) {}
}

class AreaCalculator {
  calculateArea(shape: Rectangle): number {
    return shape.width * shape.height;
  }
}

// Correct: Following OCP using interfaces
interface Shape {
  calculateArea(): number;
}

class Rectangle implements Shape {
  constructor(public width: number, public height: number) {}

  calculateArea(): number {
    return this.width * this.height;
  }
}

class Circle implements Shape {
  constructor(public radius: number) {}

  calculateArea(): number {
    return Math.PI * this.radius ** 2;
  }
}

/**
 * Calculates the area of a given shape.
 * @param shape - The shape object implementing the Shape interface.
 * @returns The area of the shape.
 */
const calculateShapeArea = (shape: Shape): number => shape.calculateArea();
```

**Explanation**: In the corrected example, the `Shape` interface allows new shapes to be added without modifying existing code in the `AreaCalculator`. This ensures that the code is open for extension (adding new shapes) but closed for modification.

#### **3. Liskov Substitution Principle (LSP)**

**Summary**: Objects of a superclass should be replaceable with objects of a subclass without affecting the correctness of the program.

**Code Example**:

```typescript
// Incorrect: Violates LSP as Square cannot fully replace Rectangle
class Rectangle {
  constructor(public width: number, public height: number) {}

  calculateArea(): number {
    return this.width * this.height;
  }
}

class Square extends Rectangle {
  constructor(size: number) {
    super(size, size);
  }

  // Square overrides behavior, breaking LSP
  setWidth(width: number) {
    this.width = width;
    this.height = width; // Forces height to equal width
  }
}

// Correct: LSP preserved by ensuring consistent behavior
interface Shape {
  calculateArea(): number;
}

class SquareLSP implements Shape {
  constructor(public size: number) {}

  calculateArea(): number {
    return this.size * this.size;
  }
}

class RectangleLSP implements Shape {
  constructor(public width: number, public height: number) {}

  calculateArea(): number {
    return this.width * this.height;
  }
}
```

**Explanation**: In the correct example, the `SquareLSP` and `RectangleLSP` implement the `Shape` interface. They can be substituted for one another, as they both provide consistent behavior without overriding methods in ways that break functionality.

#### **4. Interface Segregation Principle (ISP)**

**Summary**: Clients should not be forced to implement interfaces they do not use. Instead of one large interface, break it down into smaller, more specific ones.

**Code Example**:

```typescript
// Incorrect: A large interface forces implementation of unused methods
interface Printer {
  print(): void;
  scan(): void;
  fax(): void;
}

class SimplePrinter implements Printer {
  print(): void {
    console.log('Printing...');
  }

  scan(): void {
    // Not used, but required to implement
  }

  fax(): void {
    // Not used, but required to implement
  }
}

// Correct: Smaller interfaces for specific use cases
interface Printable {
  print(): void;
}

interface Scannable {
  scan(): void;
}

interface Faxable {
  fax(): void;
}

class PrinterOnly implements Printable {
  print(): void {
    console.log('Printing...');
  }
}
```

**Explanation**: By splitting the `Printer` interface into `Printable`, `Scannable`, and `Faxable`, we avoid forcing classes to implement methods they don't need. This ensures that classes are only required to implement what they actually use.

#### **5. Dependency Inversion Principle (DIP)**

**Summary**: High-level modules should not depend on low-level modules. Both should depend on abstractions. Additionally, abstractions should not depend on details, and details should depend on abstractions.

**Code Example**:

```typescript
// Incorrect: High-level module depends directly on a low-level class
class MySQLDatabase {
  query(sql: string): void {
    // Query the MySQL database
  }
}

class UserService {
  private database: MySQLDatabase;

  constructor() {
    this.database = new MySQLDatabase();
  }

  getUser(userId: number): void {
    this.database.query(`SELECT * FROM users WHERE id = ${userId}`);
  }
}

// Correct: High-level module depends on an abstraction
interface Database {
  query(sql: string): void;
}

class MySQLDatabaseDIP implements Database {
  query(sql: string): void {
    // Query the MySQL database
  }
}

class UserServiceDIP {
  private database: Database;

  constructor(database: Database) {
    this.database = database;
  }

  getUser(userId: number): void {
    this.database.query(`SELECT * FROM users WHERE id = ${userId}`);
  }
}

/**
 * Fetches user information from the database.
 * @param database - A Database object to perform the query.
 * @param userId - The ID of the user to retrieve.
 */
const fetchUser = (database: Database, userId: number): void => {
  const service = new UserServiceDIP(database);
  service.getUser(userId);
};
```

**Explanation**: The `UserServiceDIP` depends on the `Database` interface instead of a concrete `MySQLDatabase` implementation. This allows the service to work with any database implementation, following the DIP.

### 3. TypeScript Support

TypeScript has built-in support for **interfaces** and **abstractions** (types), making it easier to follow principles like **OCP**, **ISP**, and **DIP**. By using interfaces, abstract classes, and strong typing, TypeScript enforces adherence to these principles at compile-time, reducing the risk of violating SOLID principles.

---

### 4. Practical Use Cases

- **SRP**: Separating user management logic from file-saving logic in large-scale applications.
- **OCP**: Adding new payment methods in an e-commerce platform without modifying existing code.
- **LSP**: Ensuring that different types of shapes (circles, squares, etc.) in a drawing application can be used interchangeably.
- **ISP**: Breaking down large APIs to prevent clients from implementing unnecessary features.
- **DIP**: Making your application database-agnostic so it can easily switch between different databases like MySQL, MongoDB, etc.

---

### 5. Common Mistakes and Best Practices

- **Avoid over-engineering**: While SOLID principles are important, applying them too rigorously can lead to over-complicated code. Use them wisely.
- **Refactor gradually**: When dealing with legacy code, apply these principles incrementally.
- **Use TypeScript features**: Utilize TypeScript’s type system to ensure adherence to SOLID principles, particularly OCP, ISP, and DIP.
