# Design Patterns in TypeScript

## 1. Core Concept and Significance

**Design Patterns** are general solutions to common problems in software design. They provide proven ways to structure code that are easy to understand and maintain. These patterns are divided into three main categories:

- **Creational Patterns**: Deal with object creation mechanisms, trying to create objects in a manner suitable to the situation.
- **Structural Patterns**: Deal with object composition and help ensure that if one part of a system changes, the entire structure of the system doesn’t need to.
- **Behavioral Patterns**: Focus on how objects communicate and interact with each other.

Design patterns improve code readability, reusability, and scalability by providing tested, reusable templates for solving common design problems.

## 2. Creational Patterns

### 2.1 Singleton Pattern

#### Summary:

The **Singleton Pattern** ensures that a class has only one instance and provides a global point of access to it.

#### Code Example:

```typescript
/**
 * Singleton class: Ensures only one instance is created.
 */
class Singleton {
  private static instance: Singleton;

  private constructor() {
    console.log('Singleton instance created!');
  }

  /**
   * Provides global access to the singleton instance.
   * @returns {Singleton} The singleton instance.
   */
  public static getInstance(): Singleton {
    if (!Singleton.instance) {
      Singleton.instance = new Singleton();
    }
    return Singleton.instance;
  }
}

// Usage:
const singleton1 = Singleton.getInstance();
const singleton2 = Singleton.getInstance();

console.log(singleton1 === singleton2); // Output: true
```

#### Explanation:

- The constructor is private, ensuring that no other instance can be created outside the class.
- The `getInstance()` method provides access to the single instance.

#### Use Case:

Useful when you need to control access to resources, such as logging, configuration settings, or connection pools.

### 2.2 Factory Pattern

#### Summary:

The **Factory Pattern** provides an interface for creating objects in a super class but allows subclasses to alter the type of objects that will be created.

#### Code Example:

```typescript
/**
 * Interface representing a product.
 */
interface Product {
  create(): void;
}

/**
 * Concrete product class 1.
 */
class ConcreteProductA implements Product {
  create(): void {
    console.log('Product A created');
  }
}

/**
 * Concrete product class 2.
 */
class ConcreteProductB implements Product {
  create(): void {
    console.log('Product B created');
  }
}

/**
 * Factory class to create product based on type.
 */
class ProductFactory {
  /**
   * Factory method to create products.
   * @param type {string} Type of product to create.
   * @returns {Product} A new product instance.
   */
  public static createProduct(type: string): Product {
    if (type === 'A') {
      return new ConcreteProductA();
    } else if (type === 'B') {
      return new ConcreteProductB();
    } else {
      throw new Error('Invalid product type');
    }
  }
}

// Usage:
const productA = ProductFactory.createProduct('A');
productA.create(); // Output: Product A created

const productB = ProductFactory.createProduct('B');
productB.create(); // Output: Product B created
```

#### Explanation:

- The factory method hides the complexity of creating instances.
- The caller specifies the type, and the factory handles the creation.

#### Use Case:

Used when the creation process is complex or when you need to control object creation centrally (e.g., when managing different types of objects based on input).

### 2.3 Builder Pattern

#### Summary:

The **Builder Pattern** is used to construct complex objects step by step. It allows you to create different representations of the same object.

#### Code Example:

```typescript
/**
 * Class representing a complex product.
 */
class Product {
  public parts: string[] = [];

  addPart(part: string): void {
    this.parts.push(part);
  }

  listParts(): void {
    console.log(`Product parts: ${this.parts.join(', ')}`);
  }
}

/**
 * Builder interface declaring methods for building parts.
 */
interface Builder {
  reset(): void;
  buildPartA(): void;
  buildPartB(): void;
  getProduct(): Product;
}

/**
 * Concrete builder implementing the Builder interface.
 */
class ConcreteBuilder implements Builder {
  private product: Product;

  constructor() {
    this.reset();
  }

  reset(): void {
    this.product = new Product();
  }

  buildPartA(): void {
    this.product.addPart('Part A');
  }

  buildPartB(): void {
    this.product.addPart('Part B');
  }

  getProduct(): Product {
    const result = this.product;
    this.reset(); // Reset the builder for the next product
    return result;
  }
}

/**
 * Director class defines the order to build the object.
 */
class Director {
  private builder: Builder;

  setBuilder(builder: Builder): void {
    this.builder = builder;
  }

  buildMinimalProduct(): void {
    this.builder.buildPartA();
  }

  buildFullProduct(): void {
    this.builder.buildPartA();
    this.builder.buildPartB();
  }
}

// Usage:
const director = new Director();
const builder = new ConcreteBuilder();

director.setBuilder(builder);

director.buildMinimalProduct();
const product1 = builder.getProduct();
product1.listParts(); // Output: Product parts: Part A

director.buildFullProduct();
const product2 = builder.getProduct();
product2.listParts(); // Output: Product parts: Part A, Part B
```

#### Explanation:

- The `Builder` constructs a complex object one step at a time, allowing flexibility in object creation.
- The `Director` defines the construction process, and the `Builder` follows that process.

#### Use Case:

Useful when constructing complex objects that require multiple steps (e.g., building houses or vehicles).

## 3. Structural Patterns

### 3.1 Adapter Pattern

#### Summary:

The **Adapter Pattern** allows objects with incompatible interfaces to work together by acting as a bridge between them.

#### Code Example:

```typescript
/**
 * Class representing an incompatible system.
 */
class OldSystem {
  specificRequest(): string {
    return 'Old system output';
  }
}

/**
 * New interface that the client expects.
 */
interface Target {
  request(): string;
}

/**
 * Adapter that translates the interface.
 */
class Adapter implements Target {
  private adaptee: OldSystem;

  constructor(adaptee: OldSystem) {
    this.adaptee = adaptee;
  }

  request(): string {
    return this.adaptee.specificRequest();
  }
}

// Usage:
const oldSystem = new OldSystem();
const adapter = new Adapter(oldSystem);

console.log(adapter.request()); // Output: Old system output
```

#### Explanation:

- The adapter makes the `OldSystem` compatible with the new `Target` interface.

#### Use Case:

Useful when integrating legacy code or third-party libraries into a new system that uses different interfaces.

### 3.2 Composite Pattern

#### Summary:

The **Composite Pattern** allows you to compose objects into tree structures to represent part-whole hierarchies.

#### Code Example:

```typescript
/**
 * Component interface declaring common operations.
 */
interface Component {
  operation(): string;
}

/**
 * Leaf node of the composite tree.
 */
class Leaf implements Component {
  operation(): string {
    return 'Leaf';
  }
}

/**
 * Composite node that can have children.
 */
class Composite implements Component {
  private children: Component[] = [];

  add(child: Component): void {
    this.children.push(child);
  }

  operation(): string {
    const results = this.children.map((child) => child.operation());
    return `Branch(${results.join('+')})`;
  }
}

// Usage:
const tree = new Composite();
const branch1 = new Composite();
branch1.add(new Leaf());
branch1.add(new Leaf());

const branch2 = new Composite();
branch2.add(new Leaf());

tree.add(branch1);
tree.add(branch2);

console.log(tree.operation()); // Output: Branch(Branch(Leaf+Leaf)+Branch(Leaf))
```

#### Explanation:

- Leaf and Composite components are treated uniformly. The composite contains both simple and complex components.

#### Use Case:

Useful when representing tree structures, such as file systems or organization charts.

## 4. Behavioral Patterns

### 4.1 Strategy Pattern

#### Summary:

The **Strategy Pattern** defines a family of algorithms, encapsulates each one, and makes them interchangeable.

#### Code Example:

```typescript
/**
 * Strategy interface declaring a common method for all strategies.
 */
interface Strategy {
  execute(a: number, b: number): number;
}

/**
 * Concrete strategy for addition.
 */
class AddStrategy implements Strategy {
  execute(a: number, b: number): number {
    return a + b;
  }
}

/**
 * Concrete strategy for multiplication.
 */
class MultiplyStrategy implements Strategy {
  execute(a: number, b: number): number {
    return a * b;
  }
}

/**
 * Context class that uses a strategy.
 */
class Context {
  private strategy: Strategy;

  constructor(strategy: Strategy) {
    this.strategy = strategy;
  }

  setStrategy(strategy: Strategy): void {
    this.strategy = strategy;
  }

  executeStrategy(a: number, b: number): number {
    return this.strategy.execute(a, b);
  }
}

// Usage:
const context = new Context(new AddStrategy());
console.log(context.executeStrategy(2, 3)); // Output: 5

context.setStrategy(new MultiplyStrategy());
console.log(context.executeStrategy(2, 3)); // Output: 6
```

#### Explanation:

- The

strategy pattern decouples the algorithm from the context class.

#### Use Case:

Useful when you have multiple algorithms that can be swapped based on user input or configuration.

### 4.2 Observer Pattern

#### Summary:

The **Observer Pattern** defines a one-to-many dependency, so when one object changes state, all its dependents are notified and updated automatically.

#### Code Example:

```typescript
/**
 * Subject interface declaring methods for attaching/detaching observers.
 */
interface Subject {
  attach(observer: Observer): void;
  detach(observer: Observer): void;
  notify(): void;
}

/**
 * Observer interface that all concrete observers must implement.
 */
interface Observer {
  update(subject: Subject): void;
}

/**
 * Concrete subject class that maintains state and notifies observers.
 */
class ConcreteSubject implements Subject {
  private observers: Observer[] = [];
  private state: number = 0;

  attach(observer: Observer): void {
    this.observers.push(observer);
  }

  detach(observer: Observer): void {
    this.observers = this.observers.filter((obs) => obs !== observer);
  }

  notify(): void {
    for (const observer of this.observers) {
      observer.update(this);
    }
  }

  setState(state: number): void {
    this.state = state;
    this.notify();
  }

  getState(): number {
    return this.state;
  }
}

/**
 * Concrete observer class that reacts to subject changes.
 */
class ConcreteObserver implements Observer {
  update(subject: Subject): void {
    if (subject instanceof ConcreteSubject) {
      console.log(`Observer: Subject state changed to ${subject.getState()}`);
    }
  }
}

// Usage:
const subject = new ConcreteSubject();
const observer1 = new ConcreteObserver();
const observer2 = new ConcreteObserver();

subject.attach(observer1);
subject.attach(observer2);

subject.setState(1); // Output: Observer: Subject state changed to 1 (twice)
```

#### Explanation:

- The `Observer` watches the `Subject`, and whenever the `Subject` changes, all attached observers are notified.

#### Use Case:

Useful in event-driven systems, such as GUI components where UI elements need to update based on data changes.

### 4.3 Command Pattern

#### Summary:

The **Command Pattern** encapsulates a request as an object, allowing you to parameterize other objects with different requests, queue them, or log them.

#### Code Example:

```typescript
/**
 * Command interface declaring an execute method.
 */
interface Command {
  execute(): void;
}

/**
 * Concrete command class to turn on a light.
 */
class TurnOnCommand implements Command {
  private light: Light;

  constructor(light: Light) {
    this.light = light;
  }

  execute(): void {
    this.light.turnOn();
  }
}

/**
 * Concrete command class to turn off a light.
 */
class TurnOffCommand implements Command {
  private light: Light;

  constructor(light: Light) {
    this.light = light;
  }

  execute(): void {
    this.light.turnOff();
  }
}

/**
 * Receiver class: the light object.
 */
class Light {
  turnOn(): void {
    console.log('Light is ON');
  }

  turnOff(): void {
    console.log('Light is OFF');
  }
}

/**
 * Invoker class that stores and executes commands.
 */
class RemoteControl {
  private command: Command;

  setCommand(command: Command): void {
    this.command = command;
  }

  pressButton(): void {
    this.command.execute();
  }
}

// Usage:
const light = new Light();
const turnOnCommand = new TurnOnCommand(light);
const turnOffCommand = new TurnOffCommand(light);

const remote = new RemoteControl();

remote.setCommand(turnOnCommand);
remote.pressButton(); // Output: Light is ON

remote.setCommand(turnOffCommand);
remote.pressButton(); // Output: Light is OFF
```

#### Explanation:

- The `Command` encapsulates a request and decouples the invoker from the receiver.

#### Use Case:

Useful in building undo/redo functionality or for implementing action queues.

## 5. Best Practices and Common Mistakes

- **Pattern Overuse**: Use patterns when needed, but avoid over-complicating simple designs by forcing patterns.
- **Decoupling**: Design patterns help reduce coupling between components, making code easier to extend and maintain.
- **Code Readability**: Always aim to maintain code readability while implementing patterns.
