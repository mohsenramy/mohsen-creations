Here’s a comprehensive overview of REST vs. GraphQL, along with code examples and best practices.

## 1. Core Concept and Significance

**REST (Representational State Transfer)** and **GraphQL** are two popular approaches for building APIs.

- **REST** is an architectural style that uses standard HTTP methods (GET, POST, PUT, DELETE) to access resources. Each resource is identified by a unique URL. RESTful APIs are stateless, meaning each request contains all the information needed to process it.

- **GraphQL**, on the other hand, is a query language for APIs that allows clients to request exactly the data they need. Instead of having multiple endpoints, a GraphQL API exposes a single endpoint where clients can specify their data requirements.

**Significance**: The choice between REST and GraphQL can impact how you design your API, the flexibility of your client applications, and the efficiency of data retrieval.

## 2. Code Examples

### REST Example

```typescript
// REST API example using Express.js

import express, { Request, Response } from 'express';

const app = express();
app.use(express.json());

// Sample data
let users = [
  { id: 1, name: 'Alice' },
  { id: 2, name: 'Bob' },
];

/**
 * Get all users
 * @returns {Array} List of users
 */
app.get('/api/users', (req: Request, res: Response) => {
  res.json(users);
});

/**
 * Get a user by ID
 * @param {number} id - The user ID
 * @returns {Object} User object
 */
app.get('/api/users/:id', (req: Request, res: Response) => {
  const user = users.find((u) => u.id === parseInt(req.params.id));
  if (user) {
    res.json(user);
  } else {
    res.status(404).send('User not found');
  }
});

// Start server
const PORT = process.env.PORT || 3000;
app.listen(PORT, () => {
  console.log(`Server running on port ${PORT}`);
});
```

### GraphQL Example

```typescript
// GraphQL API example using Apollo Server

import { ApolloServer, gql } from 'apollo-server';

// Sample data
let users = [
  { id: 1, name: 'Alice' },
  { id: 2, name: 'Bob' },
];

// Define schema
const typeDefs = gql`
  type User {
    id: ID!
    name: String!
  }

  type Query {
    users: [User]
    user(id: ID!): User
  }
`;

/**
 * Resolvers to handle the GraphQL queries
 * @returns {Object} Resolved data
 */
const resolvers = {
  Query: {
    users: () => users,
    user: (_, { id }) => users.find((u) => u.id == id),
  },
};

// Create Apollo server
const server = new ApolloServer({ typeDefs, resolvers });

// Start server
server.listen().then(({ url }) => {
  console.log(`🚀 Server ready at ${url}`);
});
```

### Explanation of the Code

- In the **REST example**, we have an Express.js application that exposes two endpoints: one for retrieving all users and another for retrieving a user by ID. Each endpoint is associated with a specific HTTP method.

- In the **GraphQL example**, we use Apollo Server to define a schema that includes a `User` type and two queries: `users` and `user`. The client can request exactly the fields it needs.

## 3. TypeScript Support

TypeScript provides excellent support for defining types for REST and GraphQL APIs. You can use interfaces or types to define the shape of your data and ensure type safety throughout your API interactions.

For example, in the REST example, you could define a `User` interface:

```typescript
interface User {
  id: number;
  name: string;
}
```

In the GraphQL example, you can leverage TypeScript to infer types from your GraphQL schema using libraries like `graphql-codegen`.

## 4. Practical Use Case

**Scenario**: An e-commerce application

- **REST**: If your application requires a simple CRUD interface (e.g., creating, reading, updating, and deleting products), REST could be a good fit due to its simplicity and wide adoption.

- **GraphQL**: If your application requires complex queries (e.g., fetching products along with their categories, reviews, and related products), GraphQL provides the flexibility to request exactly the data needed without over-fetching or under-fetching.

## 5. Common Mistakes and Best Practices

### Common Mistakes

- **Over-fetching/Under-fetching**: With REST, clients often receive more data than needed or have to make multiple requests to gather all required data. With GraphQL, this is minimized, but poorly designed queries can still lead to performance issues.
- **Poorly Defined Endpoints**: In REST, not defining clear and consistent endpoints can lead to confusion and misuse.

### Best Practices

- **REST**:

  - Use HATEOAS (Hypermedia as the Engine of Application State) to provide clients with links to related resources, improving discoverability.
  - Keep endpoint names consistent and descriptive.
  - Use appropriate HTTP status codes to indicate the outcome of API requests.

- **GraphQL**:
  - Use fragments to minimize redundancy in queries.
  - Define clear types and schemas to ensure clients know what data is available.
  - Implement pagination and filtering to handle large datasets efficiently.
